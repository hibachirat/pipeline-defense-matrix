Pipeline Defense Matrix

Twenty-one security layers mapped to where they sit in a CI/CD pipeline, cross-referenced against 133 tools with enterprise and zero-cost paths for each, and tested against fourteen well-documented incidents from Equifax to the npm worms of 2026. Built on the premise that no single control stops everything — so the question is what each layer catches, what it misses, and what the next one has to cover. Includes a cross-language map of where each ecosystem executes dependency code, and a glossary.

A free license and a free deployment are not the same thing

The distinction matters most exactly where a commercial team works. Self-hosted open-source tools — Trivy, Semgrep CE, Gitleaks, zizmor, osv-scanner, Syft, cosign, Dependency-Track, Checkov — run against a private repository at no cost, because you host them. Hosted free tiers usually do not. CodeQL, runner egress monitoring, GitHub secret scanning, and most behavioral package scanners are free on public repositories and billed on private ones.

The badge on each row reflects that, not open-source status. Free on private repos means you can point it at a commercial codebase for nothing. Free for OSS only means the free tier stops at public repositories — still worth knowing, because a public-repo trial is often the fastest route to a proof of concept and a purchase approval, but not something to plan a private pipeline around.

A rule worth extracting: build inputs versus test data

A common and sound policy is to keep binaries out of source repositories, storing them in an artifact repository where they are scanned on the way in. That policy would not have caught xz, and the reason generalizes usefully.

The fixtures were encrypted — a substitution cipher and compression for the first stage, an RC4-style decryptor implemented in awk for the second. There was no package name, no version, and no coordinates to match against an advisory, so a CVE-based scanner had nothing to work with regardless of feed freshness. A behavioral scanner fares no better: high-entropy compressed binary data in a compression library’s test corpus is indistinguishable from legitimate test data, and entropy heuristics would flag every file in that directory equally.

What the policy actually buys is governance rather than detection, and that is still worth having. A binary in an artifact repository is a declared, named, versioned object with an uploader identity and a timestamp, and adding one is a reviewable change. A file committed under a test directory renders as “Binary files differ” and gets skimmed past.

The sharper rule this case argues for: anything in the repository that the build path reads is a build input and needs source-grade scrutiny, whatever its file type. Test fixtures the test suite reads are one risk class. Test fixtures the build reads — which is exactly what the trojaned macro did at configure time — are another entirely, and almost nobody draws that line. The general version is that generated files shipped inside release artifacts are a review-free zone by convention: autotools tarballs carry configure, Makefile.in and bundled m4, none of it reviewed and none of it in version control. The same shape appears in minified JavaScript bundles, vendored dependency trees, generated protobuf code, and lockfiles nobody diffs against their manifest.

Three patterns that cut across all twelve

Signing attests to identity, never to correctness. Three of these — SolarWinds, Ultralytics, and CHAINDROP — produced artifacts that were validly signed or attested by the legitimate publisher and were malicious anyway, because the compromise sat upstream of the signing step. CHAINDROP is the starkest: it compromised maintainer GitHub accounts, so the legitimate release workflow ran and npm published packages carrying valid provenance, and the worm minted fresh attestations using OIDC tokens scraped out of runner memory. Provenance was worse than useless there — it supplied a false legitimacy signal that defeated tooling keyed on “is this package signed?” Any matrix scoring artifact signing as a mitigation has to say where in the pipeline the compromise occurred.

Mutable references caused three of them. xz shipped a tarball that differed from git; tj-actions had its version tags retargeted; Ledger reached users through a floating CDN version. Immutability of what you consume — commit-SHA pins, hash-locked manifests, subresource integrity — is the highest-leverage single control across the whole set.

Detection barely functioned. SolarWinds was found through an MFA enrollment anomaly at one customer. xz was found by a database engineer investigating unexplained SSH latency. Codecov was found by one customer who checked a published hash after nine weeks. Only tj-actions was caught by a control built for the purpose, and that control was runner egress monitoring — not any scanner.

The honest read on spend

Layer coverage does not scale with price. The free stack and the $500k stack detect broadly similar things; what money buys is consolidation, support, compliance reporting, and someone to escalate to. Three layers are the exception, where paid tools measurably outperform free ones: registry gating with quarantine, behavioral malicious-package analysis, and base image hardening. The first two depend on threat databases that are expensive to build and keep current, and no free tool matches them for breadth. The third is simply labour — somebody has to rebuild thousands of images every time an upstream package changes. If the budget only stretches to part of this matrix, those three are where it earns the most.

Read this table correctly — it is not an argument against buying tools

Path A scores highest because the decisive control in most of these incidents was architectural rather than purchased: pin by digest, hold no standing credentials, wait before adopting a new version, build from source control. Those cost nothing to license. What the table measures is available capability, not achieved capability — every Path A control is free to adopt and expensive to operate consistently across many teams, with no vendor to escalate to and no report to hand an auditor. One further correction for a commercial codebase: Path A’s prevention holds on private repositories, because pinning, cooldowns, disabled install scripts, and building from source control are self-hosted or procedural. Its detection degrades, because runner egress monitoring and the deepest free SAST engine are free only on public repositories. Assume the free path costs something once the repositories are private.

The genuinely surprising column is D. The enterprise suites miss the entire CI/CD pipeline security cluster, because none of the large AppSec platforms analyze workflow definitions or monitor runners. The two most recent pipeline compromises on this list — a poisoned build cache and retargeted version tags — are invisible to a quarter-million-dollar platform and are caught by tools that cost nothing. If you buy Path D, budget separately for that gap.

The closest thing to a formula

There is no magic formula, and anyone selling one is selling something. But these seven properties, taken together, cover all fourteen incidents — and every one of them is free to license. They are not a tool list; they are properties your pipeline either has or does not.

So what does the money actually buy?

Not incident coverage — the table above is clear about that. What a budget buys is the difference between a control existing and a control being enforced, which is the real problem at organizational scale.

Enforcement across teams. You can set a cooldown in one repository’s Renovate config for free. Enforcing a quarantine policy across four hundred repositories, with exceptions tracked and audited, is what a registry gateway is for.

Breadth in the two layers where free tools are genuinely thinner. Behavioral malicious-package detection and continuously rebuilt hardened base images both depend on work somebody has to do every day, and the free options are narrower rather than equivalent.

Private-repository coverage. Several of the strongest free controls — runner egress monitoring, the deepest SAST engine — are free only on public repositories. For a commercial vendor, that half of Path A is not actually free.

Evidence. Findings correlation at volume, and the audit trail a CRA technical file or a customer security questionnaire demands. A free stack can be more secure and still fail a procurement review, because nothing produces the report.

The honest sequencing, then: implement the seven properties first, because they are free and they cover the incidents. Buy tools second, to enforce and evidence what you have already implemented. Doing it in the other order is how organizations end up with a large licensing spend and unpinned workflow actions.

Section 06

Where each ecosystem executes dependency code

The formula’s fourth property — disable lifecycle scripts — reads as npm advice, but it generalizes across every language, and the generalization is cleaner than the per-ecosystem mechanics. One question sorts them all: does acquiring or building a dependency execute dependency-authored code before you run your own program?

Tier 1Executes on acquisition

Merely resolving a dependency is enough to be compromised. This is where every worm campaign in Section 03 lives, and also where the tooling is now strongest — all of these have an allowlist or a refusal flag.

The rule that falls out of the table

Where you can turn execution off, allowlist it. Where you cannot, isolate the build. Six of the eleven have no official disable at all — Maven, Gradle, Conan, vcpkg, RubyGems and Cargo — and their vendors say so plainly. Apache’s own security page: “the Maven security model assumes you trust the pom.xml… it is up to you to provide the required isolation.” Microsoft on MSBuild: “unknown build logic should be assumed to be capable of executing arbitrary code in the build environment.” Gradle: build scripts “can also execute arbitrary code during the configuration phase.” RubyGems: “installing a gem runs someone else’s code on your machine, with your privileges.” These first-party admissions are better evidence than any third-party analysis.

Three findings worth carrying into an architecture review. Java’s attack surface is plugins, not dependencies — archives are inert at resolution, while plugins, build extensions and .mvn/extensions.xml load third-party code before any build logic runs, and most SCA tooling scans the dependency block and ignores the plugin block entirely. .NET has no install scripts but does have build execution — the PowerShell hooks were legacy, but packages still inject MSBuild targets that run during build, and analyzers load directly into the compiler process. Composer has the strongest allowlist in the industry, default-deny and fail-closed since December 2021, roughly four and a half years ahead of npm.

One correction worth making explicitly, because the documentation invites the error: in Cargo, package.build = false disables the build script only for the package that declares it. A consumer cannot set it for a dependency. There is no consumer-side flag, on stable or nightly, and the sandboxing effort did not continue past 2024.

Prior art, so you need not invent the taxonomy

Ladisa, Plate, Martinez and Barais, “SoK: Taxonomy of Attacks on Open-Source Software Supply Chains,” IEEE Security & Privacy 2023, is the best citation — it frames this exact axis and names “prevent script execution” and “isolation of build steps” as distinct safeguards. Duan et al., NDSS 2021, includes a per-registry comparison with an explicit install-hook row, though only for three interpreted-language registries. Ohm et al., DIMVA 2020, maps trigger points against a dataset of real malicious packages.

Worth knowing what does not cover this axis, since both get cited as though they do: the OpenSSF S2C2F framework and the OpenSSF and CISA “Principles for Package Repository Security” contain no requirement addressing install-time or build-time code execution. S2C2F is oriented to post-acquisition scanning, inventory and updating; the Principles are organized around authentication and authorization.

Section 08

Traps in the tool list

Things that break a matrix assembled from search results or last year's notes. Each of these was verified this month.

Brakeman is non-commercial-use only

The license grants use "only for the purpose of non-Commercial Use." Commercial use requires a purchased license. This is the single most common trap in a "free Rails security stack" — it is not free for a software vendor.

Five entries are dead or deprecated

Terrascan archived November 2025. tfsec merged into Trivy. chain-bench unreleased since January 2024. git-secrets has zero published releases and 93 open issues. Phylum no longer exists independently — its technology was acquired by Veracode in January 2025.

Free tiers that are not free enough to matter

Docker Scout free tier covers one repository. Safety CLI's free plan is explicitly "not recommended for commercial purposes" and ships a degraded database. Chainguard's free tier is 5 images via Catalog Starter, or 43 images at :latest only — no version pinning. gitleaks-action requires a free license key for organization accounts and has been proprietary since v2.0.0; invoke the MIT CLI in a run: step instead.

Copyleft in the toolchain

Renovate self-hosted, StepSecurity secure-repo, and TruffleHog are AGPL-3.0. hadolint is GPL-3.0. Semgrep CE, Opengrep, and njsscan are LGPL. All fine invoked as CI binaries; all matter if you fork them, vendor them, or offer them as a service. AFL++ is AGPL with an explicit carve-out — the fuzzing harness itself stays Apache-2.0.

Your scanner is also a supply chain

In March 2026 an attacker force-pushed malicious commits over all 77 trivy-action tags and all 7 setup-trivy tags, plus Trivy binaries v0.69.4–v0.69.6 and Docker Hub images. The payload scraped runner process memory and 50+ filesystem paths for SSH keys, cloud credentials, and Kubernetes tokens. Safe versions: Trivy v0.69.3 or earlier, trivy-action v0.35.0, setup-trivy v0.2.6. This is the strongest available argument for pinning actions to commit SHAs rather than tags.

Section 09

Evaluating the behavioral layer

Malicious-package and behavioral analysis is the newest layer in this matrix and the one buyers have least practice assessing. Two questions decide most evaluations, and neither is answerable from a datasheet. Worked through below against a widely deployed tool in the category, since the answers generalize to its competitors.

Depth · by ecosystem

How deep does the analysis go on compiled languages?

The framing usually needs adjusting first. Of the ecosystems that feel “compiled,” only JVM and .NET actually ship binaries. Go modules, Rust crates, and Swift packages all distribute source, so static analysis applies as directly as it does to npm.

For Maven, Socket states it analyzes “every file in the package, including the compiled binary JAR, the source code JAR, and any accompanying metadata,” and its NuGet threat research demonstrably produces findings on compiled DLLs including IL metadata. Whether the automated pipeline decompiles bytecode or analyzes it directly is not published.

What is documented is that coverage is measurably shallower there. Obfuscated-code detection is marked unsupported for Maven, NuGet, Go, and Crates. The maintainer-takeover signal is npm and Packagist only. Swift, C/C++, Julia, Dart, and Elixir are CVE-only despite carrying a GA label. Ask any vendor in this category for its per-ecosystem alert matrix, not its ecosystem list.

Scale · build time

Will it slow a build with thousands of dependencies?

Largely no, and the architecture is why. Socket states it “preemptively scans every open-source package, so by the time a customer triggers a scan, Socket has already analyzed nearly every package in their dependency tree.” Analysis happens once per package-version, centrally, and is shared across all customers. A build-time scan is dependency-tree resolution plus a database lookup, not code analysis — which is why large trees do not scale linearly.

Pull-request scans diff against the last head scan by default. The default CLI mode is asynchronous; a report flag makes it blocking.

The exception is full application reachability analysis, which runs in your own runner. Its published defaults set the envelope: a 10-minute timeout and an 8GB memory limit per run. That is a real runner-sizing requirement. Lower reachability tiers are precomputed server-side and add no build time. The general lesson: ask which analysis happens on the vendor's infrastructure and which happens on yours.

Two caveats to carry into any evaluation of this layer

No vendor in this category publishes scan-latency benchmarks, so build-time impact has to be measured during a trial rather than negotiated from a datasheet. And central pre-computation has a specific failure mode: independent testing has found declared dependencies silently absent from reports, traced to package indexing gaps. If a package-version is not in the index it is not analyzed, and the absence is quiet rather than loud — so a proof of concept should verify that every declared dependency actually appears, not merely that findings look plausible. Tools in this layer also position themselves as complementary to CVE-based SCA rather than replacing it; they alert on supply chain attacks, malware, and typosquats rather than on every known vulnerability.

Section 10

The compliance clock

The regulatory picture moved in opposite directions across the Atlantic this year. For a commercial software vendor, plan for EU obligations tightening and US federal obligations fragmenting.

EU · 11 September 2026

CRA reporting goes live

Article 14 reporting obligations become applicable. Actively exploited vulnerabilities and severe incidents must be reported to your member state CSIRT: 24 hours early warning, 72 hours full notification, 14 days final report. The 24-hour clock is what breaks existing processes — it needs a path from discovery to filing that does not route through multi-day legal review.

EU · 11 December 2027

Full CRA obligations

Essential cybersecurity requirements, vulnerability handling, conformity assessment, CE marking. SBOM in a machine-readable format covering at least top-level dependencies, held in technical documentation and produced to market surveillance authorities on request — not published. Germany's BSI TR-03183 v2.1.0 is the most concrete preview, naming CycloneDX 1.6 and SPDX 3.0.1 with per-component SHA-256 hashes.

US · 23 January 2026

OMB M-26-05 relaxed the mandate

Rescinded the mandatory software attestation requirements of M-22-18 and M-23-16. There is no longer a government-wide SSDF self-attestation on the CISA Common Form, and SBOM submission is no longer universally mandated. Do not remove these controls. Agencies now set risk-based requirements individually, which may fragment one form into many; the CRA mandates SBOM regardless; and enterprise customers increasingly require attestations contractually.
